# 세션02에서 하는 일 — 쉬운 설명과 실제 실험 방법

**후속 갱신(2026-09-30):** 사용자가 토큰 상한 확대 재시험을 요청했다. 현재 다음은 [32K·전체 문맥80응답 재시험](LONG_GENERATION_V01_KO.md)이며 [향후 예산 원칙](GENERATION_BUDGET_POLICY_KO.md)을 따른다. 기존 결과는 보존하고 새16문맥96회 점검은 미승인 보류한다. 아래 내용은 그 이전 설명·준비·실행 기록이다.

## 목적

우리 연구의 큰 질문은 **“모델을 적은 비트로 바꿨을 때 추론이 길어지는 현상을, 일반적인 가중치 교란으로도 재현할 수 있을까?”**다. 아직 그 가설을 본격적으로 시험한 단계는 아니다. 지금 세션02에서는 원본 모델과 AWQ 모델을 준비하고, 비교 과정의 수치·종료·채점이 믿을 만한지 확인한다.

BF16은 비교 기준 모델이다. AWQ-W3는 가중치 값을 더 적은 단계로 표현하는 양자화 조건이다. 이번 코드는 그렇게 바뀐 가중치를 BF16 연산으로 평가하므로, 실제3비트 전용 커널의 속도나 메모리 절감 실험은 아니다.

‘기능적 동등성 미인증’에서 중요한 비교는 좌표 변환 전후다. 같은 물체를 센티미터와 미터로 기록해도 물체가 달라지지 않아야 하듯이, 가중치를 비교하려고 수치의 표현을 바꾸는 과정은 모델의 행동을 크게 바꾸지 않아야 한다. BF16 연산에서는 작은 반올림 차이가 생길 수 있으므로 그 영향이 얼마나 큰지 확인한다. 반면 BF16과 AWQ가 서로 다른 결과를 내는 것은 연구 대상이다.

## 실제로 한 실험

| 순서 | 무엇을 했나 | 알아보려는 것 |
|---|---|---|
| R0 | 저장 calibration으로 AWQ28계층 처리, 짧은2문제를 BF16/AWQ로 생성 | 모델 연결·양자화·결과 저장이 작동하는가 |
| 난도 시험 | 자체20문제×2모델×2시드=80응답, 최대4096토큰 | 문제를 실제로 풀 때 정답·길이·종료가 어떻게 다른가 |
| 마스크 확인 | 설치 코드의 작은 CPU attention mask를 비교 | 문맥4096 경계에서 어떤 과거 입력이 가려지는가 |
| 고정 prefix12회 | 같은 기존 풀이 앞부분2개에 B/B_repeat/S/Q/C/Cw를 적용 | 양자화와 좌표 변환이 다음 토큰 분포를 각각 얼마나 바꾸는가 |
| 저장 logit 감사 | 이미 저장한12개 배열을 사용자 CPU에서 재계산 | 보고된 수치와 실제 저장 배열이 일치하는가 |
| 종료 prefix6회 | BF16 종료 직전·동일길이 AWQ 문맥에 B/B_repeat/Q를 적용 | 똑같은 종료 문맥에서도 AWQ가 EOS를 밀어내는가 |

R0의 생성4개는 모두128토큰 상한에서 끝났다. 비유하면 제한 시간이 너무 짧아 답안지를 걷은 상황이다. 따라서 그 결과만으로 정답률이나 원래 끝날 길이를 알 수 없었다. 약0.6%의 계층 상대 RMS는 별도의 Pile calibration128×512토큰에서 측정한 변환 진단이며, 짧은 산수2문제의 정확도 손실이 아니다.

난도 시험에서는 D1~D5 각각4문제를 만들고 두 모델이 seed42/43으로 답을 생성했다. temperature=.6, top-p=.95, 응답당4096토큰 상한이었다. 이 난도는 자체 분류이며 MATH 공식 난도가 아니다. Pile은 일반 텍스트 calibration 자료로 사용했고 MATH-500 시험은 아직 하지 않았다.

| 난도 시험80응답 | BF16 40개 | AWQ 40개 |
|---|---:|---:|
| 자연 EOS 종료 |25|12|
| 상한에서 잘림 |15|28|
| 최종 정답 확인, 자동+수동 |25|12|

상한 응답을 최종 오답이라고 확정하지 않았다. 생각 중 정답 숫자가 한 번 등장한 것도 최종 정답으로 세지 않았다. 원래 자동 정답 집계는22/11이고, 종료 후 형식 미판정4개를 검토해 수동 보완한 수가25/12다. 원래 자동 난도 판정은 모두 INCONCLUSIVE로 보존하며, 수동 보완표에서는 BF16 D1만8/8 자연 종료·정답 조건을 충족했다.

이 표는 이 자체 문제·시드·예산에서 **AWQ가 더 자주 상한까지 이어 썼다**는 관측이다. 전체 자연 길이 증가율·공식 난도 통과 경계·H1의 성공을 입증하지 않는다. 실제 생성 중 문맥4096 경계의 마스크 영향도 미확정이다.

## 같은 문맥을 넣는 실험은 어떻게 하나

모델은 앞에 나온 토큰들을 보고 다음 토큰마다 점수를 준다. 이 점수가 logit이고, 이를 확률로 바꾼 것이 다음 토큰 분포다. prefix는 이미 주어진 질문과 풀이 앞부분이다.

일반 생성에서는 BF16이 다른 단어를 하나 고르면 그 다음부터 문맥도 달라진다. 그러면 나중의 차이가 모델 때문인지, 이미 달라진 앞 문장 때문인지 한 번에 구분하기 어렵다. 그래서 저장된 풀이 앞부분을 고정하여 여러 모델 상태에 똑같이 넣었다. 새 답을 계속 쓰게 하지 않고 지정한 위치들의 다음 토큰 점수만 읽었다.

12회 진단에서는 D2-03/D3-01의 BF16 생성 앞2048토큰을 재사용했다. B는 원본, S는 scale만 적용, Q는 AWQ, C는 원래 좌표로 복원, Cw는 보조 파라미터까지 원복한 상태이며 B_repeat로 원본 반복도 비교했다. 전체 입력 길이는2119/2127이고, 각129개 위치의 전체 어휘 점수를 저장했다. B 반복은 정확 일치로 보고됐지만 좌표 변환 전후의 분포에는 작은 차이가 남았다.

후속 CPU 감사에서 좌표 비교의 최상위 토큰 변경5건은 모두 공동1위와 관련된 것으로 확인했다. 예를 들어 원래 A가 단독1위였는데 변환 후 A와 B가 동점1위가 된 경우다. 그래도 확률 분포 전체가 같아진 것은 아니므로 동등성 PASS로 바꾸지 않았다.

## 최근6회 진단의 구체적 방법과 결과

D2-03의 BF16 응답은2425번째 생성 토큰에서 EOS로 끝났고 AWQ 응답은4096토큰 상한까지 이어졌다. 다음 두 문맥을 준비했다.

1. BF16이 EOS를 내기 바로 전까지 쓴2424토큰.
2. AWQ가 쓴 앞2424토큰.

각 문맥에는 원래 질문71토큰이 붙어 전체2495토큰이 된다. 두 문맥의 **길이는 같지만 내용은 다르다.** EOS를 미리 입력에 넣지 않았다. 각각을 B/B_repeat/Q에 넣어 총6회 계산하고, 마지막129개 위치를 관측했다. cache를 쓰지 않는 full-sequence 계산이며 실제 자유 생성을 재실행한 것은 아니다.

| 넣어 준 문맥 | BF16의 필터 후 EOS 확률 | AWQ의 필터 후 EOS 확률 |
|---|---:|---:|
| BF16이 답을 끝내기 직전 |1|1|
| 같은 길이의 AWQ 문맥 |0|0|

마지막 위치에서 T=.6·top-p=.95의 float64 필터를 적용한 값이다. **AWQ도 BF16의 종료 문맥을 받으면 EOS만 후보로 남았다.** AWQ 문맥을 받은 BF16도 그 자리에서는 EOS를 후보로 두지 않았다. 이 한 사례에서 종료 문맥 자체를 주었을 때 AWQ가 EOS를 제거한다는 설명을 지지하지 못했다.

다만 AWQ가 왜 다른 문맥을 만들었는지, 그 차이가 왜 오래 이어졌는지는 아직 모른다. BF16 문맥의 앞129개 위치 중5곳, AWQ 문맥의16곳에서 B/Q의 최상위 토큰이 달랐다. 최종 위치의 EOS가 같다는 결과를 전체 분포·정확도·자연 길이가 같다는 뜻으로 확대하지 않는다.

## 현재 위치와 다음 작업

지금은 **세션02의 실행·진단 결과를 확보하고, 후속 실험에 쓸 비교 기준을 검증하는 단계**다. 결과가 없어 준비만 반복하는 상태는 아니다. 그러나 기능적 수락 기준·실제 생성/cache의 타당도·평가기 일반화·후속 재현 기준이 남아 model_ready=false다. 연구가 성공하거나 실패했다고 판정할 단계도 아니다.

이번 요청으로 [새16문맥 좌표 점검](FUNCTIONAL_HOLDOUT_V01_KO.md)의 입력·수치 기준·예산·실행기를 준비했다. 모델 출력으로 고르지 않은 새 풀이 문맥16개에서 좌표 변환의 영향을 확인하는 제한된 다음 작업이다. 최대96회 forward·새 생성0이며 별도 실행 승인 전이다. 기존 실험·데이터 준비·토크나이저 검사를 다시 실행하지 않는다.

사용자가 마지막으로 입력한 `git switch`와 `git pull --ff-only`는 브랜치·파일 갱신 명령이다. 그 명령을 입력했다는 보고를 새 GPU 실험 결과로 기록하지 않는다.

수치와 검증 깊이의 원 기록은 [난도 원본 검토](DIFFICULTY_EVIDENCE_REVIEW_20260929_KO.md), [고정 prefix 검토](FIXED_PREFIX_RESULT_REVIEW_20260930_KO.md), [저장 배열 감사 보고 검토](LOGITS_AUDIT_REVIEW_20260930_KO.md), [종료 문맥 검토](TERMINATION_PREFIX_RESULT_REVIEW_20260930_KO.md)를 따른다. 사용자가 제출한 JSON·생성 ID·코드/설정과 내부 집계를 대조한 범위이며, 이 환경에서 사용자 GPU·가중치·원시 logit 배열을 직접 재실행하거나 읽은 검증과 구분한다.
